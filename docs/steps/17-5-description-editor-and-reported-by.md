# Step 17, after G-5: the description editor and "Reported by"

Design: [case-management/13-plain-case-design.md](../case-management/13-plain-case-design.md), section 12. Built 2026-11-11 at the owner's request, after [17-4](17-4-plain-case-browser-checks-and-guides.md).
The live application (Docker) was upgraded to this version on 2026-11-11 (item 11 below): migrations 0019, 0020 and 0021 ran there.

1. **Removed from the Register a case form:** six small hints (under Type of case, Classification, Lead investigator, Supervisor, Description, and the line "Use fictional data only in this demonstration
   system" under the heading). The rules behind them did not change.
2. **Description is a button** that opens a small compose window in the middle of the screen, like an email: a header, the case's title and type, the writing area, **Save** (needs at least 10 characters),
   **Discard** and a character count. Closing the window drops the changes of that session; the saved text stays.
3. **A formatting bar**, like Gmail's: undo, redo, font, size, bold, italic, underline, text colour, alignment, numbered list, and a "more" menu (bulleted list, remove formatting). Built on Tiptap.
4. **Two copies of the description.** `description` stays plain text (reports, search, the assistant and the history read it); the new `description_html` (migration 0020) is the formatted copy, shown on the
   case page. The server cleans it (`app/casemgmt/rich_text.py`, library `nh3`: only the bar's formatting survives; values of colour, font, size and alignment are checked one by one) and the page cleans it
   again (DOMPurify). Existing cases show their plain text.
5. **Reported by** (migration 0021): name, phone, email, address of the person who reported the case, none required, plus **Unknown** (cannot be combined with details; ticking it clears what was typed). A bad
   email address blocks registering. The case page's About box shows the details, "Unknown", or "not recorded". Not yet in the signed PDF report.
6. **How it was checked.**
   - 20 new backend tests (`tests/test_cm_styled_description.py`): the formatting is kept; ten kinds of attack (scripts, event handlers, images, links, frames, style tricks) are cleaned out; blank is nothing;
     both copies are stored and the plain one stays plain; the reporter (details, none, unknown, unknown plus details refused, bad email refused). Breaking the style filter on purpose made three of them fail.
   - 6 new front-end tests (the editor's toolbar and what it reports; the viewer cleans scripts, handlers, images and links; the Overview shows the reporter three ways and the description both ways).
   - Browser checks against the real backend on a throwaway database: the popup opens focused with its toolbar; short text keeps Save off; bold, underline, colour, font, size, alignment and a list are applied;
     Save, reopen (formatting kept), Discard (changes dropped); the case is registered and the case page shows the styled description. **Reported by:** typing a bad email blocks registering; ticking Unknown
     clears and switches off the fields; a case with details, one with Unknown and one with nothing each show correctly on the case page. No console errors.
7. **Found on the way:** on this computer the preview API's port owner shows as 0, so a restart must stop the old server by its command line; a Supervisor cannot lead a case, so a lead must be chosen when a
   Supervisor registers one. The walkthrough and acceptance scripts were updated for the Description button (`write_description` helper).
8. **Tasks removed from the screens (owner request, 2026-11-11).** No Tasks tab on the case, no *Assigned tasks* menu item or page, no *Open tasks* link on the Overview, no task counter or "Needs your attention" box on the dashboard, no task columns or boxes on the performance and administration pages, and no task section in the guides (their later sections were renumbered; the task picture was removed). Notices about earlier tasks, if any exist, now lead to the case. **Only the screens changed:** the task part of the backend (its tables, API and data) is untouched, so nothing was deleted and the screens can be brought back; tell me if the backend part should be removed too. The browser scripts no longer create tasks (the live-notice check now uses a comment by the Sub Investigator on the Investigator's note); the tour checks that no Tasks link or tab exists. Front end: 75 tests pass.
9. **Similar-case search: the 100 past cases and the case-side bar (owner question, 2026-11-11: "why did you remove 100 cases").** Nothing was removed: the live database still holds all 100 imported Supreme Court judgments (2,672 passages, all embedded). The preview uses a separate throwaway database that had only 2 sample past cases, so the search there looked emptied. The 100 judgments and their passages, pages, provisions, entities and events were **copied** (read-only from the live database) into the preview database; the search page then showed 102 cases and 52 matches for a test query. Then a real fault was found in the **Insights** tab and **Offence sections** of a registered case: they found no past case at all, even for text that mirrors a judgment, because a passage had to score **0.80** against a judgment passage, a bar meant for comparing two whole judgments. Measured with the real model on the 100 judgments: related text scores 0.70 to 0.78, unrelated text stays under 0.66, so 0.80 could never be reached. The case side now has its own setting, `case_similar_passage_min_similarity` (default **0.70**, `CASE_SIMILAR_PASSAGE_MIN_SIMILARITY`), never stricter than the whole-document bar; uploads and the search page are unchanged. Result on the preview: the pension test case finds 3 past pension judgments, the demonstration bank-fraud case finds 11 (each with the matched passages, the provisions cited and why). One new backend test (the bar is capped, and a looser passage matches only under the lower setting; breaking it made the test fail). The tour now waits for the Insights results, so the guide picture shows them (the old one showed a spinner); 22 guide pictures were retaken (the dashboard and all-cases pictures were left, because the preview now holds test cases).
10. **Case assistant: "The chat model took longer than 280 seconds to answer" (owner request, 2026-11-11).** Reproduced on the preview: a real question took the full 280 s and failed (the model runs on this laptop's CPU, no graphics card it can use). Measured with the real model: reading the question was the slow part (12 words a second, because Ollama chose 6 of the 12 processor threads; all 12 gave 21 a second), and writing was about 3 words a second. Fixes: (1) the model now uses all processor threads (`CHAT_THREADS`, 0 = all); (2) the assistant sends 3 passages instead of 4 and asks for answers of at most 100 words instead of 150, and the model's writing cap is 300 tokens instead of 400. Result on the preview with the same kind of question: **120 s and 163 s** (the first includes loading), where the old setting needed more than 280 s and failed. The 280 s limit is kept on purpose: some browsers stop waiting after about 300 s. A busy computer (tests, Docker) can still slow an answer; a faster model or a graphics card is the next step if answers must be quicker. New backend test (the thread count is sent; 0 means all processors); the waiting message now says 2–3 minutes.
11. **The preview and the live application were cleared and the live application upgraded (owner requests, 2026-11-11).** "Delete all case data and login details, keep the usernames and passwords, keep only the similar-case data", then "delete old version". **Preview** (`casesdb_e2e`): all cases and everything about them, the audit trail (which holds the login records, restarted empty), lockout counters, the test integration source, uploads and the two dummy past cases were removed. **Live** (`casesdb`): the same, then the Docker application was rebuilt and the database migrated 0018 to 0021 (the old repository tables are gone). **Kept in both:** every account with the same username and password (a fingerprint of all usernames and password hashes was identical before and after), the organisation and station, the worker's job log, and the 100 imported past judgments with all their search data. Backups of both databases before the changes are in `backups/` (`...-before-clear`, `...-preview-before-clear`, `...-live-before-upgrade`; the folder is git-ignored). The clean-up is one all-or-nothing transaction (`clear_case_data_v2.sql`: TRUNCATE of every table except the kept ones, after dropping and restoring the foreign keys that the access history has to case tables). Checked on the live application in a browser: all seven logins, no Tasks menu, the Description popup with its formatting bar, Reported by, and the similar-case search over 100 cases (58 matches for a test query); no case was created. The old OneDrive copy of the project (`NEPAL_PRJ`) was not touched.
12. **Every old account removed from the live application (owner request, 2026-11-11, option 2).** A new Super Admin `superadmin` was created first (random password, stored only in the git-ignored `.dev-credentials.txt`) and tested on the live application; then the seven earlier accounts (`admin`, `analyst`, `viewer`, `demo.admin`, `demo.supervisor`, `demo.arun`, `demo.meena`) were deleted in one transaction (`remove_old_accounts.sql`: their station links and access-history rows removed, and the "started by" marks of the worker job log cleared; the log itself and the 100 past judgments kept). All seven old logins now answer 401; `superadmin` logs in. A backup taken just before is in `backups/` (`...-live-before-account-removal`). The preview database keeps its own test accounts (`demo.*`, `kh.*`). Other accounts are now made by the Super Admin on the People and stations screen (the officer must be in the officer register).
13. **Officers create their own login; clearance can be changed (owner request, 2026-11-11: "they can create their own login").** The owner's sentence leaves the safety design open, so this follows the existing rules (docs/case-management/12): the login page offers **Create your own login** (`/create-account`); it works only for an officer in the register whose full name matches and who has no account yet (one identical message for every refusal, so the register cannot be explored; a few attempts per hour per computer); the account starts with the least access (Viewer, `public` clearance, at the officer's register station, no case open to it); the Super Admin and the station's Administrators and Supervisors are told (`account.self_registered`) and raise the **role** (never above the register's ceiling) and the new **clearance** (migration 0022, `POST /people/accounts/{id}/clearance`: people below the caller, at the caller's station, never one's own, never above the caller's clearance, with a reason, kept in the access history). `SELF_REGISTRATION=false` switches it off. The sign-in page lost its last wording from the removed Git-style design (repository, clone, merge). Checks: 7 backend tests for sign-up and clearance (breaking the name check, the "already has an account" check or the clearance ceiling each made a test fail), 8 front-end tests, and a browser run on the preview (wrong name refused; right name creates the login; it logs in as Viewer/public and sees the 100 past judgments; the Super Admin is told and raises the clearance on the People screen). The test accounts were removed afterwards. **Note:** nobody can sign up until the Super Admin has entered officers in the register (People and stations, Register of officers; one by one or by CSV file).
14. **Profile of a login (owner request, 2026-11-11: "add profile updation when login is created").** Each person fills in and updates their own **email, phone and job title** (migration 0023: four columns on `users`, all optional, plus `profile_updated_at`). They can do it while creating their own login (two optional fields on the form), and any time on the new **My profile** page (top-right account menu, `/kh/profile`). Name, officer ID, rank, station, role and clearance come from the register and the people above, and are only shown there. Until a person has saved their profile once, the dashboard shows **Complete your profile**, then it goes. The people above see job title, email and phone in the People list. `POST /auth/profile` changes only the caller's own profile, refuses every other field, lets an empty value clear a field, and the audit trail keeps which fields changed, never their values. Checks: 7 backend tests (one found that clearing a field with an empty value was refused: fixed; loosening the "only these three fields" rule made a test fail), 15 front-end tests, and a browser run on the preview (sign up with a profile: no prompt; sign up without: prompt, fill in, saved, prompt gone; menu opens the profile; the Super Admin sees the contact details). Test accounts were removed afterwards.
15. **Teams on the profile (owner request, 2026-11-11: "profile should have to look the teams").** The **My profile** page has a new section **Teams I am on (n)**: the cases whose team the person belongs to or leads, with their part, status, priority, classification and last activity, each linking to its case (the same list as My cases on the dashboard, no new backend); an empty list says "Not on any team yet". 4 front-end tests for the page (one new), a browser check with sample data (nothing written to the database). If "teams" was meant as the colleagues of the person's station, or the team of one case on its own profile, that is not built: tell me.
16. **Profile photo (owner request, 2026-11-11: "build it").** Each person can add a photo on **My profile** (`Upload a photo` / `Change photo` / `Remove photo`). Migration 0024: `users.photo_data` (a small JPEG, loaded only when asked for) and `photo_updated_at`. The server accepts only JPEG, PNG or WebP (2 MB, 24 million pixels), decodes it and draws it again as a 256 x 256 JPEG, so camera and location tags and anything hidden after the picture do not survive (`app/auth/photos.py`, with Pillow). Only the owner can set or remove it; only logged-in people of the same organisation can fetch it; the audit trail records that it changed, never the picture. The photo shows in the top bar, My profile, the People list and wherever a person's name is shown (`PersonName`: team, history, comments), with initials when there is none. Checks: 14 backend tests (breaking the re-drawing made 4 fail, breaking the same-organisation check made 1 fail), 3 new front-end tests, and the accounts tour in a browser (upload, top bar, People list). Not included: cropping on screen before saving (the middle of the picture is used), photos in the colleague pickers and the officer dashboard headings (initials there).
17. **Chat inside a case (owner request, 2026-11-11: "once the case is created, people who are in this group can chat with each other in the group and individually").** A **Chat** tab on every case for the people on its team (any part, while they are on it): **The team** (everyone on the case team) and a **private conversation with each other member** (only the two). Migration 0025: `case_messages` (permanent: the database refuses to change or delete a row) and `case_chat_reads` (how far each person has read each conversation: the only part that changes). Unread counts per conversation and a badge on the tab; one unread notice per conversation (`chat.message`, which leads to the conversation), cleared when it is read; new messages appear within a few seconds (the page asks every 4 s while it is in front). Not in the conversations: somebody who oversees the case without being on the team, and a person taken off the team (access ends at once). An archived case keeps its conversations read-only. Decided for the owner (say if one is wrong): messages are permanent and cannot be edited or deleted, like every record in a case; chat is not part of the case history chain (it is not case work); the audit trail records that a message was sent, never its text; reading is not audited (it is polled). Checks: 10 backend tests (breaking the team-only check made 1 fail, breaking the privacy of private messages made 2 fail), 6 front-end tests, and a browser tour with four people in separate windows (`chat_tour.py`: a message to the team with the unread badge, a private message that only its two people and nobody else see, the Supervisor without the tab). Not built: files or pictures in messages, editing, "typing" indicators, @mentions, search in chat, messages across cases.
18. **Governance screen removed (owner request, 2026-11-12: "remove Governance").** The administration menu entry **Governance** and its page (audit chain with Verify now and Sign now, the scheduled checks, retention policies, the list of legal holds, the go-live settings) were removed from the screens, and with them the six front-end functions only that page used. **The backend is unchanged:** the worker still recomputes and signs the audit chain every day (a broken chain still raises a notice, which now leads to Audit logs), legal holds and retention decisions are still made on each case's Overview, and `GET /api/v1/admin/governance` and the other endpoints remain. The go-live settings are still checked by `scripts.readiness_check`. The browser scripts lost their Governance step and picture, and the administrator guide its section (the later sections were renumbered).
19. **Withdrawn files: gone for the team, highlighted for the Supervisor (owner request, 2026-11-12: "it should only be deleted on the investigator, sub investigator, analyst, viewer, but it should be present and highlighted on the Supervisor dashboard; he cannot delete anything from that case").** "Deleted" is the existing *Withdraw with a reason* (nothing is ever really deleted). Now: (a) only the Investigator who leads the case can withdraw; the Supervisor, Administrator and Super Admin cannot (403, no button); (b) a withdrawn file is hidden from the team in every view (files list, detail and download by id, reports, search, assistant, imports, timeline) exactly like a sealed file; (c) the overseers always see it in the Files tab, in red, with a banner and a line *Withdrawn by <person> on <date>: <reason>*; the old *Show withdrawn files* switch was removed. Decision recorded as 19 in docs/case-management/13-plain-case-design.md §12. Tests: 5 existing backend tests changed to the new rule, new assertions for the Supervisor's view and 403 (mutation-checked: allowing the Supervisor to withdraw, or showing the file to the team, each makes a test fail), a front-end test of the red row, and step 12 of the browser walkthrough (35 steps pass).
    Released to the live application on 2026-11-12 (no database migration; backup ackups/20261112T*-live-before-withdrawn-release); the throwaway database used for the walkthrough was dropped. Backend 601 and front-end 97 tests pass.
20. **The case number can be changed (owner request, 2026-11-12: "KH-2026-0001 -> make this as editable", answered: *change the number after registration*).** The Supervisor, Administrator or Super Admin of a case changes its number with a reason (a pencil next to the number on the case page). The old number is kept for ever (migration 0026: table `case_number_changes`, permanent; the `case_families` trigger now also allows `display_id`; a new history kind `case_renumbered`), still finds the case in the search, shows as *Formerly ...* under the title, and is never reused; typed numbers can't look like the system's own `CODE-YYYY-NNNN`. Decision 20 in docs/case-management/13-plain-case-design.md section 12. Tests: 6 new backend tests (`tests/test_cm_case_number.py`: rights, rules, old number search, permanence at database level, archived case; mutation-checked), one front-end test of the dialog, and a browser tour (`frontend/e2e/case_number_tour.py`, 4 steps pass).
